# Билет 23. Архитектура CPU и GPU, параллелизм, память и зависимости

## CPU

**CPU** оптимизирован под малую задержку выполнения одного потока и сложную управляющую логику. Обычно у процессора немного мощных ядер. Каждое ядро содержит АЛУ, регистры, L1/L2-кэш, блоки управления, а общий L3-кэш разделяется между ядрами. Контроллер памяти управляет обменом с ОЗУ.

Главная идея CPU - быстро выполнять последовательный код с ветвлениями и зависимостями. Для этого используются многоуровневые кэши, предсказание переходов, конвейеризация, внеочередное исполнение и переименование регистров. В источнике приведены примерные задержки доступа: L1 hit - около 4 тактов, L2 hit - около 10 тактов, L3 hit - около 40-80 тактов. ОЗУ намного медленнее, поэтому кэш нужен для сглаживания разрыва между скоростью ядра и памяти.

## GPU

**GPU** оптимизирован не под latency одного потока, а под throughput: выполнение огромного числа однотипных операций над разными данными. GPU состоит из вычислительных кластеров и потоковых мультипроцессоров (**SM**). Каждый SM содержит много простых вычислительных ядер, общий быстрый ресурс вроде shared memory/L1 и выполняет группы потоков.

Модель выполнения - **SIMT**:

$$
Single\ Instruction,\ Multiple\ Threads.
$$

Потоки объединяются в **варпы**. Внутри варпа потоки выполняют одну инструкцию над разными данными. Если потоки одного варпа расходятся по разным веткам `if`, возникает branch divergence: ветки выполняются по очереди, а часть потоков простаивает.

В источнике для NVIDIA Volta указано: L1 hit - около 28 тактов, L2 hit - около 193 тактов. Это больше, чем у CPU, но GPU скрывает задержку иначе: пока один варп ждет данные из памяти, планировщик ставит его в конец очереди и запускает другой готовый варп.

## Массивно-параллельная модель и память

CPU старается ускорить один поток: сложное ядро, сильные кэши, спекуляция и переупорядочивание. GPU старается держать занятыми тысячи потоков: если часть потоков ждет память, другие продолжают вычисления. Поэтому для GPU важны:

- высокая occupancy, то есть достаточно активных варпов;
- регулярные обращения к памяти;
- **coalescing** - объединение обращений соседних потоков к соседним адресам в один крупный доступ, например к сегменту 32/64/128 байт;
- использование shared memory для повторно используемых данных.

Отличие кэширования: у CPU кэш - главный способ уменьшить latency каждого доступа. У GPU кэш проще и больше подчинен пропускной способности; отдельные простые ядра не имеют таких развитых индивидуальных кэшей, как CPU-ядра.

## Зависимости по данным

Типичный hazard - **RAW**:

$$
Read\ After\ Write.
$$

Он возникает, когда инструкция читает значение, которое предыдущая инструкция еще не записала.

На CPU зависимости в основном скрываются аппаратно:

- pipeline stalls или bubbling - вставка ожиданий;
- forwarding - передача результата между стадиями конвейера;
- out-of-order execution - выполнение независимых инструкций раньше;
- register renaming - устранение ложных зависимостей.

На GPU подход другой:

- синхронизация потоков внутри блока, например `__syncthreads()`;
- очереди команд: внутри одной очереди порядок сохраняется;
- события: одна операция сигнализирует о завершении, другая ждет;
- атомарные операции при конкурентной записи в общий адрес.

Итог: CPU хорош для сложного последовательного кода с малой задержкой; GPU хорош для регулярных массово-параллельных задач. CPU борется с памятью кэшами и сложным исполнением, GPU - большим числом варпов и переключением между ними.
